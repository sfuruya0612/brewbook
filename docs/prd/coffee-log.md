# コーヒー記録アプリ PRD

Created: 2026-09-21
Model: Claude Fable 5.1
Status: Draft

## 概要

自宅で淹れたコーヒーを記録するための Web アプリケーションを作る。
豆を買った店、豆の商品、商品を買った購入、コーヒーを淹れた抽出の 4 種類の記録を登録し、抽出から使った豆と、買った店 (登録している場合) をたどれるようにする。
Frontend は Flutter で Web を先行し、Backend は Rust で Cloudflare Workers 上に置く。
統計とグラフ、管理者用の Web 画面も初回スコープに含める。

## 用語

本節は、決定者と記録の種類を区別するために筆者が追加した。

- **所有者**：このリポジトリの所有者であり、本 PRD の要求を決めた人。
  2026-09-21 の会話の相手。
- **管理者**：アプリを運用し、管理者画面で利用者を作成する人。
  初回は所有者が兼ねる。
- **利用者**：アプリにログインして自分の記録を扱う人。
  複数人いる。
- **筆者**：本 PRD を書いた Claude Fable 5.1。
- **店**：豆を買った焙煎所や小売店。
- **商品**：豆の銘柄。
  同じ商品を複数回買える。
- **購入**：商品を 1 回買った記録。
  1 袋に対応する。
- **抽出**：コーヒーを 1 回淹れた記録。
  1 つの購入に紐づく。
- **アーカイブ**：論理削除。
  記録を既定の一覧から外すが物理的には消さない。

## 目的

この PRD が満たされたとき、次が実現される。

- 利用者は、店、商品、購入、抽出の 4 種類の記録を Web ブラウザから登録、閲覧、編集、アーカイブできる。
- 利用者は、抽出 1 件から、使った豆 (購入と商品) と、その豆を買った店 (登録している場合) をたどれる。
- 利用者は、期間を選んで抽出と購入の統計をグラフで見られる。
- 利用者は、パッケージの写真を購入に添付して閲覧できる。
- 利用者は、パスワードを使わず、パスキーだけでログインできる。
- 利用者は、自分の全記録をエクスポートでき、アカウントと全データを自分で削除できる。
- 利用者ごとにデータが分離され、他の利用者の記録は見えない。

## 成功指標

| 指標 | 目標 | 測定方法 |
| --- | --- | --- |
| 抽出の登録に必要な画面の数 | 抽出一覧 (ホーム) から保存完了までの最短経路で表示する画面 (ルーターに登録した画面) が、ホームを含めて 3 つ以内 | Flutter の統合テストで最短経路を実行し、表示した画面の種類の数を数える。戻る操作は最短経路に含めない。ダイアログ、ボトムシート、保存完了の通知 (スナックバーなど) は画面に数えない |

| API の応答時間 | 店、商品、購入、抽出の一覧と単件取得の p95 が 200 ms 以内 | Worker がリクエストごとに経路名と処理時間をログに出し、リリース後に Workers Logs の保持期間の全量 (Workers Free プランは 3 日、Workers Paid プランは 7 日。2026-09-21 に Cloudflare のドキュメントで確認) で p95 を集計する。写真の取得と統計の API は含めない |

利用者は、自宅でコーヒーを淹れ、複数の焙煎所や店で豆を買う個人である。
利用者は複数人いてよいが、データを共有する機能は持たない。
アカウントは管理者が管理者画面で作成する。

| ID | 場面 | 行動 |
| --- | --- | --- |
| UC-1 | 初めて使うとき | 管理者から受け取った登録用リンクを開き、パスキーを登録してログインする |
| UC-2 | 2 回目以降にアプリを開くとき | パスキーでログインする |

| UC-5 | コーヒーを淹れたとき | 使った豆 (購入) を選び、抽出日時、豆の量、湯量、湯の温度、時間、抽出方法、挽き目、評価、感想を登録する |

## スコープ

- 店、商品、購入、抽出の登録、閲覧、編集、アーカイブ、アーカイブ解除
- 購入の購入日と抽出の抽出日時の記録

- 統計画面と統計の API (月別と日別の抽出回数と豆の消費量、購入金額と重量、抽出条件と評価の関係、期間の切り替え) と、購入の画面での購入ごとの評価の推移

- UI の日本語と英語の対応
- Flutter Web のビルド成果物と Rust の Backend を 1 つの Cloudflare Worker としてデプロイ (Static Assets)
- 管理者用の Worker のデプロイ
- iOS 向けにビルドできる状態の維持 (CI では検証せず、iOS 対応時に確認する)

- 利用者間のデータ共有、公開ページ、フォロー機能
- 利用者による自由登録 (セルフサインアップ)

- オフラインでの記録と後からの同期
- 為替変換 (通貨コードは記録するが換算しない)

- 1 購入への複数枚の写真

- Android 向けのビルドと配布
- 独自ドメインの取得 (workers.dev のホスト名を使う。管理者 Worker に Cloudflare Access を掛けられない場合の代替案は「## 未確定論点」)

- 管理者 Worker での Cloudflare Access の JWT 検証

## 機能要求

優先度は **Must** (無いと成立しない)、**Should** (初回リリースに含める)、**Could** (含めなくてよい) の 3 段階とする。
各要求の受け入れ基準は、自動テストで真偽を判定できる形で書く。

### エラー応答の規約

受け入れ基準で使う HTTP ステータスコードの意味を次に定める。

| コード | 意味 |
| --- | --- |
| 400 | 入力が不正 (必須の欠落、型や範囲の違反、形式の違反) |
| 401 | 未認証 (セッションが無いか無効) |
| 403 | `Origin` ヘッダが同一オリジンでない |
| 404 | 指定した ID の記録が存在しないか他の利用者に属する。または指定した登録用トークンが存在しない |
| 409 | 状態の矛盾 (アーカイブ済みの参照、最後のパスキーの削除、使用済みトークンの再使用、署名カウンタの後退) |
| 410 | 期限切れ (登録用トークン、チャレンジ) |

写真のアップロード用 URL の期限切れは R2 が判定し、Backend は関与しない (FR-10)。

### 認証と利用者

#### FR-1 登録用トークンによるパスキーの登録 (Must)

管理者が発行した登録用トークンを持つ利用者は、パスキーを登録してログイン状態になれる。
初回の利用者 (UC-1) と、パスキーを全て失った利用者 (UC-14) の両方がこの経路を使う。

受け入れ基準は次の通りとする。

- `/register?token=<トークン>` を開くと、パスキー登録の画面が表示される (ウィジェットテストで判定する)。
- 存在しないトークンでは登録の API が 404、使用済みのトークンでは 409、期限切れのトークンでは 410 を返し、パスキーは登録されない。
- 登録が成功すると、トークンは使用済みになり、同じトークンで 2 回目の登録を試みると 409 を返す。
- 登録が成功した時点でセッションが発行され、以後の API 呼び出しが認証済みとして扱われる。
- 登録するパスキーには 1 文字以上 50 文字以下の名前を付ける。
  名前が無いか範囲外なら 400 を返す。

#### FR-2 パスキーによるログイン (Must)

登録済みのパスキーを持つ利用者は、ユーザー名やパスワードを入力せずにログインできる。

受け入れ基準は次の通りとする。

- ログインのチャレンジ発行の API は入力を持たず、ユーザー名も受け取らない。
- ログイン画面でパスキーを選ぶと、サーバーが発行したチャレンジへの署名が検証され、セッションが発行される。
- 署名の検証に失敗した場合は 400、チャレンジの期限が切れている場合は 410、チャレンジが再利用された場合は 409 を返し、セッションは発行されない。
- 認証器の署名カウンタは W3C WebAuthn Level 3 の 7.2 節に従って検証する。
  保存値と今回の値の両方が 0 のときは検査を省略する。
  どちらかが 0 でないとき、今回の値が保存値以下なら 409 を返してログインを拒否する。
  今回の値が保存値より大きければ保存値を更新する。
- ログインが成功すると、そのパスキーの最終使用日時が更新される。

#### FR-3 パスキーの追加、名前の変更、削除 (Should)

ログイン済みの利用者は、パスキーを追加でき、名前を変更でき、2 つ以上あるときは削除できる。

受け入れ基準は次の通りとする。

- ログイン済みの状態でパスキー追加の API を呼ぶと、新しいパスキーが同じ利用者に紐づく。
  追加の API は FR-1 と同じ範囲の名前を受け取り、名前が無いか範囲外なら 400 を返す。
- パスキーの名前の変更 API で名前を変えられる。
  範囲は FR-1 と同じとし、範囲外なら 400 を返す。
- 利用者のパスキーが 1 つしかないとき、そのパスキーの削除 API は 409 を返す。
- 他の利用者のパスキーの ID を指定した削除と名前の変更の API は 404 を返す。
- パスキーの一覧 API は、各パスキーの名前、登録日時、最終使用日時を返す。

#### FR-4 ログアウト (Must)

利用者はログアウトでき、ログアウト後はそのセッションで API を呼べない。

受け入れ基準は次の通りとする。

- ログアウト API を呼んだ後、同じセッションで認証が必要な API を呼ぶと 401 を返す。
- ログアウトしたセッションの行はデータベースから削除される。

#### FR-5 利用者間のデータ分離 (Must)

利用者は自分の記録だけを読み書きできる。

受け入れ基準は次の通りとする。

- 他の利用者に属する店、商品、購入、抽出の ID を指定した取得、更新、アーカイブ、アーカイブ解除の API は、全て 404 を返す。
- 他の利用者に属する購入の ID を指定した写真の取得、アップロード用 URL の発行、アップロード完了の通知、写真の削除の API は、全て 404 を返す。
- 他の利用者に属するパスキーの ID を指定した削除と名前の変更の API は 404 を返す。
- 他の利用者に属する購入の ID を指定した評価の推移の API は 404 を返す (FR-18)。
- 一覧の API、サジェストの API、統計の API は、呼び出した利用者の記録だけを返す。

### 店

#### FR-6 店の登録と編集 (Must)

利用者は、店を登録し、編集できる。

受け入れ基準は次の通りとする。

- 店名は必須で、前後の空白を除いて空になる値では登録できない (400 を返す)。
- 住所は任意 (NULL 許容) である。
- 登録した店は一覧と単件で取得でき、店名と住所を更新できる。

### 商品

#### FR-7 商品の登録と編集 (Must)

利用者は、商品を登録し、編集できる。

商品の項目は次の通りとする。

| 項目 | 必須 | 型 |
| --- | --- | --- |
| 商品名 | 必須 | 文字列 |
| Producer | 任意 | 文字列 |
| Origin | 任意 | 文字列 |
| Region | 任意 | 文字列 |
| Process | 任意 | 文字列 |
| Variety | 任意 | 文字列 |
| Flavor Notes | 任意 | タグの集合 (FR-8) |

受け入れ基準は次の通りとする。

- 商品名は必須で、前後の空白を除いて空になる値では登録できない (400 を返す)。
- 商品名以外の項目は NULL で登録できる。
- 登録した商品は一覧と単件で取得でき、全ての項目を更新できる。

#### FR-8 Flavor Notes のタグ付け (Must)

利用者は、商品に Flavor Notes を複数のタグとして付けられる。

受け入れ基準は次の通りとする。

- 商品の登録と更新でタグ名の配列を渡すと、商品のタグはその配列で置き換えられる (配列に無い既存のタグは商品から外れる)。
- 同じ利用者の同じタグ名は 1 つのタグとして扱われ、複数の商品から共有される。
- タグ名は前後の空白を除いて比較し、空になるタグ名は 400 を返す。
- どの商品からも参照されなくなったタグは削除せず残す。
- 商品の取得結果にタグ名の配列が含まれる。
- 利用者の全タグの一覧を取得できる。

### 購入

#### FR-9 購入の登録と編集 (Must)

利用者は、商品を買った 1 回を購入として登録し、編集できる。

購入の項目は次の通りとする。

| 項目 | 必須 | 型 |
| --- | --- | --- |
| 商品 | 必須 | 商品への参照 |
| 店 | 任意 | 店への参照 (もらい物など店が無い購入は NULL) |
| 購入日 | 必須 | 日付 (`YYYY-MM-DD`)。クライアントが端末のタイムゾーンでの当日を既定値として入れる |
| Roast | 任意 | 文字列 (焙煎度) |
| Roast Date | 任意 | 日付 (`YYYY-MM-DD`) |
| 価格 | 任意 | 0 以上の整数 (通貨の最小単位) と ISO 4217 の通貨コード (既定値 JPY) |
| 重量 | 任意 | 0 以上の整数 (グラム) |
| 写真 | 任意 | R2 上のオブジェクトへの参照 (FR-10) |

受け入れ基準は次の通りとする。

- 商品と購入日は必須で、欠けていれば 400 を返す。
- 店は省略でき、省略した購入は店を持たない。
  更新で店の ID に null を送ると店を外せる。
- 存在しないか他の利用者に属する商品または店の ID を指定すると 404 を返す。
- アーカイブ済みの商品または店を指定した新規登録は 409 を返す。
- 価格を指定して通貨コードを省略すると、サーバーは通貨コードを JPY として保存する。
  通貨コードを指定するときは ISO 4217 の 3 文字の英大文字だけを受け付ける (それ以外は 400)。
- 重量と価格は 0 以上の整数だけを受け付ける (それ以外は 400)。
- 購入の取得結果には、商品の項目を `product`、店の項目を `shop` のネストしたオブジェクトとして含める。
  店が無い購入では `shop` は null になる。
- 購入の一覧は購入日の降順で返り、購入日が同じときは ID の昇順で返る (ADR-0002 のカーソル)。

#### FR-10 パッケージ写真の添付 (Must)

利用者は、購入に 1 枚のパッケージ写真を添付し、差し替え、削除できる。

写真の API は全て購入 ID をパスに取る。

| 操作 | API |
| --- | --- |
| アップロード用 URL の発行 | `POST /api/purchases/<購入 ID>/photo/upload-url` (申告サイズを受け取る) |
| アップロード完了の通知 | `POST /api/purchases/<購入 ID>/photo` (発行時に返したオブジェクトキーを受け取る) |
| 写真の取得 | `GET /api/purchases/<購入 ID>/photo` |
| 写真の削除 | `DELETE /api/purchases/<購入 ID>/photo` |

受け入れ基準は次の通りとする。

- 上の 4 つの API は、購入 ID が存在しないか他の利用者に属するとき 404 を返す (FR-5)。
- 差し替えは、既に写真がある購入に対して URL の発行と完了の通知を行うことで実現する。
- クライアントは、端末が復号できる画像 (Web では JPEG、PNG、WebP) を JPEG に変換し、長辺 2048 px 以下に縮小してからアップロードする。
  Flutter 側の自動テストで、長辺 4,000 px の PNG と JPEG の入力から、JPEG かつ長辺 2048 px 以下の出力が得られることを検証する。
- クライアントは、アップロード前に変換後のサイズをサーバーへ申告する。
  申告サイズが 5 MB (5,000,000 バイト) を超えると、サーバーは 400 を返し URL を発行しない。
- サーバーは、Content-Type が `image/jpeg`、Content-Length が申告サイズ、有効期限が 5 分の条件で署名した PUT 用の URL を返す。
  クライアントはこの URL に対して直接アップロードする。
- アップロード用の URL の対象キーは `pending/<利用者 ID>/<UUID>.jpg` とする (ADR-0003)。
- アップロード完了をサーバーに通知すると、サーバーはオブジェクトの存在、サイズ (申告サイズと一致し 5 MB 以下)、Content-Type を確認してから購入に紐づける。
  確認に失敗した場合は紐づけず、オブジェクトを削除し、400 を返す。
- 紐づけでは、サーバーが R2 バインディングでオブジェクトを取得して `users/<利用者 ID>/purchases/<購入 ID>/<UUID>.jpg` に保存し、`pending/` 側のオブジェクトを削除し、購入の `photo_key` に保存先のキーを保存する (ADR-0003)。
  紐づけ後の `photo_key` が `pending/` で始まらないことを自動テストで検証する。
- 写真の取得は `/api/purchases/<購入 ID>/photo` で行い、認証済みの利用者だけができる。
  他の利用者の購入の写真は 404 になる。
- 写真を差し替えると古いオブジェクトは削除される。
  写真を削除すると購入の写真参照は NULL になり、オブジェクトは削除される。
- 有効期限の秒数は設定値とし、テストでは短い値を注入して、期限切れの URL への PUT を R2 (ローカルでは wrangler のローカル R2) が 4xx で拒否することを検証する。
  期限の判定は R2 が行い、Backend は関与しない。

### 抽出

#### FR-11 抽出の登録と編集 (Must)

利用者は、コーヒーを淹れた 1 回を抽出として登録し、編集できる。

抽出の項目は次の通りとする。

| 項目 | 必須 | 型 |
| --- | --- | --- |
| 購入 | 必須 | 購入への参照 |
| 抽出日時 | 必須 | 日時 (ISO 8601、UTC)。クライアントが現在時刻を既定値として入れる |
| 豆の量 | 任意 | 0 以上の小数 (グラム、小数第 1 位まで) |
| 湯量 | 任意 | 0 以上の小数 (グラム、小数第 1 位まで) |
| 湯の温度 | 任意 | 0 以上の小数 (摂氏、小数第 1 位まで) |
| 時間 | 任意 | 0 以上の整数 (秒) |
| 抽出方法 | 任意 | 文字列 (ドリッパーや器具の名前) |
| 挽き目 | 任意 | 文字列 (グラインダーの設定値) |
| 評価 | 任意 | 整数 (1 から 5) |
| 感想 | 任意 | 文字列 |

購入と抽出日時以外の項目は、2026-09-21 に所有者が任意 (NULL 許容) と決めた。

受け入れ基準は次の通りとする。

- 購入と抽出日時は必須で、欠けていれば 400 を返す。
- 豆の量、湯量、湯の温度、時間は負の値を 400 で拒否する。
- 存在しないか他の利用者に属する購入の ID を指定すると 404、アーカイブ済みの購入を指定した新規登録は 409 を返す。
- 豆の量、湯量、湯の温度は小数第 2 位以下を持つ値を 400 で拒否する。
- 時間は 0 以上の整数、評価は 1 から 5 の整数だけを受け付ける (それ以外は 400)。
- 抽出の取得結果には、購入の項目を `purchase` のネストしたオブジェクトとして含め、その中に `product` と `shop` を含める (UC-6)。
  店が無い購入では `shop` は null になる (FR-9)。
- 抽出の一覧は抽出日時の降順で返り、抽出日時が同じときは ID の昇順で返る (ADR-0002 のカーソル)。

### 横断

#### FR-12 アーカイブ (Must)

利用者は、店、商品、購入、抽出をアーカイブし、アーカイブを解除できる。
アーカイブは論理削除であり、物理的には削除しない。

受け入れ基準は次の通りとする。

- アーカイブした記録は、既定の一覧に含まれない。
- 一覧の API にアーカイブ済みを含めるパラメータを指定すると、アーカイブ済みの記録も返る。
- アーカイブした記録は単件取得でき、アーカイブ解除で既定の一覧に戻る。
- 親 (店、商品、購入) をアーカイブしても、子 (購入、抽出) はアーカイブされず、子から親をたどれる。
- アーカイブ済みの店、商品、購入を新規の購入や抽出の参照先に指定すると 409 を返す (FR-9、FR-11)。

#### FR-13 過去の入力値のサジェスト (Should)

利用者が自由記述の項目を入力するとき、同じ利用者が過去に入力した値が候補として表示される。

対象の項目は、商品の Producer、Origin、Region、Process、Variety、購入の Roast、抽出の抽出方法と挽き目とする。

受け入れ基準は次の通りとする。

- 項目名と入力中の文字列を指定してサジェスト API を呼ぶと、その利用者がその項目に過去に入力した値のうち、前後の空白を除いた値が入力中の文字列で始まるもの (大文字と小文字を区別しない) を、重複を除いて最大 20 件返す。
- 入力中の文字列が空のときは、その項目の全ての値を重複を除いて最大 20 件返す。
- 候補は、その値を持つ記録 (商品、購入、抽出) の `updated_at` のうち最も新しいものの降順に並べ、それが同じときは値の Unicode コードポイントの昇順に並べる (ADR-0006)。
  21 件以上あるときは先頭の 20 件を返す。
- アーカイブ済みの記録の入力値も候補に含める。
- 他の利用者の入力値は含まれない。
- 候補の選択は任意であり、候補に無い値も入力できる。

#### FR-14 全記録のエクスポート (Must)

利用者は、自分の全記録を 1 つの JSON ファイルとしてダウンロードできる。

受け入れ基準は次の通りとする。

- エクスポートには、ADR-0006 で定める利用者データの全テーブル (店、商品、タグ、商品とタグの対応、購入、抽出) の、アーカイブ済みを含む全行と全列が含まれる。
  パスキー、セッション、チャレンジ、登録用トークンは含めない。
- 写真は、購入の `photo_key` と、写真取得 API のパス (FR-10) として含まれる。
  写真の実体は含めない。
- エクスポートした JSON をテスト専用の復元処理で別の利用者に取り込むと、user_id と photo_key に含まれる利用者 ID を除いて、上記の全テーブルの全行と全列が元の記録と一致する (成功指標の測定方法)。

#### FR-15 アカウントと全データの削除 (Must)

利用者は、自分のアカウントと全データを削除できる。

受け入れ基準は次の通りとする。

- 削除の API を呼ぶと、ADR-0006 の全テーブル (users、registration_tokens、passkey_credentials、webauthn_challenges、sessions、shops、products、flavor_tags、product_flavor_tags、purchases、brews) からその利用者に属する全行 (`user_id` がその利用者の行) が物理削除され、R2 上のその利用者の全オブジェクト (紐づけ済みと紐づけ前の両方) が削除される。
  webauthn_challenges のログイン用の行は `user_id` を持たないため削除の対象外とし、有効期限で失効する (ADR-0006)。
- 削除後、その利用者の全セッションは無効になり、API 呼び出しは 401 を返す。
- 削除は元に戻せないため、クライアントは確認ダイアログで明示的な確認ボタンを押させる。
  確認ボタンを押さずに削除 API が呼ばれないことを Flutter の自動テストで検証する。

#### FR-16 UI の日本語と英語の対応 (Should)

UI の文言は日本語と英語で表示できる。

受け入れ基準は次の通りとする。

- 端末またはブラウザの言語設定が日本語のとき日本語、それ以外のとき英語で UI が表示される。
- UI の文言は全て翻訳ファイル (ARB) に置く。
  `lib/` 以下の UI コードで、Text、TextSpan、InputDecoration の labelText と hintText と helperText と errorText、Tooltip の message、SnackBar の content、AppBar の title に文字列リテラルを直接渡していないことを静的検査で検証する。
  ログ、テストコード、翻訳キー、URL は検査の対象外とする。
- 項目名は日本語 UI では日本語で表示する。
  対応は Producer が生産者、Origin が生産国、Region が地域、Process が精製方法、Variety が品種、Roast が焙煎度、Roast Date が焙煎日、Flavor Notes がフレーバーノートとする。
  日本語の ARB ファイルにこの 8 つの訳語が値として存在することを CI の静的検査で確認する。

#### FR-17 管理者画面による利用者の作成とトークンの発行 (Must)

管理者は、Cloudflare Access で保護した管理者画面で、利用者を作成し、その利用者の登録用トークンを発行できる。
既存の利用者に対しても再発行できる (UC-14)。
管理者画面は利用者向けの Worker とは別の Worker (管理者 Worker) が配信する (ADR-0008)。

受け入れ基準は次の通りとする。

- 管理者画面は `brewbook-admin.<アカウントのサブドメイン>.workers.dev` で配信し、Worker 単位の Cloudflare Access 保護 (Workers のダッシュボードの Access タブ、または `worker` 種別のセルフホスト型アプリケーション) で管理者 Worker 全体を保護する (ADR-0008)。
  Access のポリシーは所有者のメールアドレスだけを許可する。
  ポリシーの内容は自動では検証できないため、デプロイ手順のチェック項目として管理者が Access の管理画面で確認する。
- 管理者 Worker は Access の JWT を検証しない (所有者の決定)。
  デプロイ後の確認タスク (mise のタスク。ADR-0009) で、認証なしで管理者画面の URL を取得すると Access のログイン画面へリダイレクトされる (302) ことを検証する。
- 管理者画面は管理者 Worker がサーバー側で生成する HTML のフォームとし、Flutter と JavaScript を使わない (ADR-0008)。
  フォームの送信先の経路を管理者 API と呼ぶ。
  管理者 API は利用者向けの Worker のセッション認証を使わず、Cloudflare Access だけで保護する。
- 管理者画面で、利用者の一覧 (表示名、作成日時、パスキーの数) を見られる。
  `wrangler dev` に対する結合テストで、利用者を作成した後の一覧の HTML にその表示名が含まれることを検証する。
- 管理者画面で、表示名 (1 文字以上 50 文字以下) を入力して利用者を作成できる。
  範囲外の表示名は 400 を返す。
  表示名は管理者が利用者を識別するためだけに使い、利用者向けの Worker のどの API の応答にも含めない (自動テストで検証する)。
- 管理者画面で、利用者を選んで登録用トークンを発行できる。
  発行した登録用リンク (`/register?token=<トークン>` の完全な URL) は発行直後の応答に 1 回だけ含め、一覧を含む他のどの応答にも含めない (結合テストで検証する)。
  存在しない利用者の ID を指定すると 404 を返す。
- 登録用トークンの有効期限は発行から 24 時間とする。
- 登録用トークンの生の値はデータベースに保存せず、ハッシュだけを保存する。
- 既存の利用者を指定してトークンを発行でき、そのトークンで登録したパスキーはその利用者に追加される。
- 管理者 Worker は利用者向けの Worker と同じ D1 データベースをバインディングで参照し、users テーブルと registration_tokens テーブルを読み書きし、passkey_credentials テーブルを読む。
  それ以外のテーブルは読み書きしない。
  管理者 Worker の SQL は 1 か所で組み立て、SQL に現れるテーブル名がこの 3 つだけであることを単体テストで照合する。

### 統計

#### FR-18 統計とグラフ (Should)

利用者は、期間を選んで自分の抽出と購入の統計をグラフで見られる。

対象は次の 4 つとする。

| 統計 | 内容 | 表示 |
| --- | --- | --- |
| 抽出回数と豆の消費量 | 期間内の抽出の件数と豆の量 (グラム) の合計を、日別または月別に集計する。豆の量が NULL の抽出は件数に数え、消費量には加えない | 統計画面の棒グラフ |
| 購入金額と重量 | 期間内の購入の価格と重量 (グラム) の合計を、通貨コードごとに日別または月別に集計する。価格が NULL の購入は金額に、重量が NULL の購入は重量に加えない | 統計画面の棒グラフ (通貨ごとに分ける) |
| 抽出条件と評価の関係 | 期間内の評価を持つ抽出について、豆の量、湯量、湯の温度、時間のそれぞれと評価の組を返す。集計しない | 統計画面の散布図 (条件ごとに 4 つ) |
| 購入ごとの評価の推移 | 1 つの購入に紐づく抽出の抽出日時と評価を、抽出日時の昇順で返す。評価が NULL の抽出は含めない。期間で絞らない | 購入の画面の折れ線グラフ |

期間の扱いは次の通りとする。

- 初期表示は当月 (端末のタイムゾーンでの当月 1 日から当日まで) を日別で表示する。
- 3 か月、6 か月、12 か月、全期間に切り替えられ、これらは月別で表示する。
  3 か月、6 か月、12 か月は当月を含む直近の月数とする。
  全期間は開始日と終了日を省略して呼び、最初の記録から最後の記録までを返す。
- 任意の開始日と終了日を指定できる。
  期間が 62 日以下なら日別、それ以外は月別で表示する。
- 抽出日時は UTC で保存されているため、クライアントは端末のタイムゾーンの UTC オフセット (分) を API に渡し、サーバーはそのオフセットで日と月を区切る。
  オフセットは端末のローカル時刻から UTC を引いた分数とし、日本標準時は +540 とする。
  購入日はタイムゾーンを持たない日付なので、オフセットを受け取らずそのまま区切る。
- 集計と散布図は、その行自身がアーカイブ済みの抽出と購入を含めない。
  参照先の購入がアーカイブ済みでも、抽出自身がアーカイブ済みでなければ含める。

API は次の 4 つとする。

| 操作 | 経路 | クエリパラメータ |
| --- | --- | --- |
| 抽出回数と豆の消費量 | `GET /api/stats/brews` | 開始日、終了日、粒度、UTC オフセット |
| 購入金額と重量 | `GET /api/stats/purchases` | 開始日、終了日、粒度 |
| 抽出条件と評価の関係 | `GET /api/stats/brew-ratings` | 開始日、終了日、UTC オフセット |
| 購入ごとの評価の推移 | `GET /api/purchases/<購入 ID>/rating-history` | 無し |

受け入れ基準は次の通りとする。

- 開始日と終了日は `YYYY-MM-DD` の文字列で、どちらも省略できる。
  開始日が終了日より後のときは 400 を返す。
  開始日は端末のローカル時刻での日付として扱い、抽出の API では UTC オフセットを使って UTC の範囲に変換する。
- 粒度は `day` または `month` の文字列で必須とし、それ以外は 400 を返す。
- UTC オフセットは -840 から 840 の整数 (分) で必須とし、それ以外は 400 を返す。
- `GET /api/stats/brews` は、区間ごとに区間のキー、抽出の件数 (整数)、豆の量の合計 (小数第 1 位までの数値) を返す。
  区間のキーは日別なら `YYYY-MM-DD`、月別なら `YYYY-MM` の文字列とし、区間はキーの昇順で並べる。
  記録の無い区間は返さない。
- `GET /api/stats/purchases` は、区間と通貨コードの組ごとに区間のキー、通貨コード、価格の合計 (整数)、重量の合計 (整数)、購入の件数 (整数) を返す。
  区間のキーの形式と並び順は抽出と同じとし、同じ区間では通貨コードの昇順で並べる。
- `GET /api/stats/brew-ratings` は、期間内の評価を持つ抽出ごとに、抽出の ID、豆の量、湯量、湯の温度、時間、評価を返す。
  条件が NULL の項目は null で返し、クライアントは null の条件をその散布図に描かない。
- `GET /api/purchases/<購入 ID>/rating-history` は、その購入に紐づく評価を持つ抽出の、抽出の ID、抽出日時、評価を抽出日時の昇順で返す。
  存在しないか他の利用者に属する購入の ID は 404 を返す。
  アーカイブ済みの購入も指定できる (単件取得と同じ扱い。FR-12)。
- 既知の記録を投入した自動テストで、上の 4 つの API の応答が期待値と一致し、他の利用者の記録とアーカイブ済みの記録が含まれない。
  日と月の境界をまたぐ抽出日時と、オフセット +540 と -300 の組み合わせを期待値に含める。
- 統計画面は、初期状態で当月の日別の棒グラフを表示し、3 か月、6 か月、12 か月、全期間、任意の期間に切り替えられる (ウィジェットテストで判定する)。
- 集計の SQL は、アーカイブの条件と `user_id` の条件を含めて 1 か所で組み立てる (ADR-0006)。

## 非機能要求

### 性能

- 店、商品、購入、抽出の一覧と単件取得の API は p95 で 200 ms 以内に応答する (成功指標)。
- 写真はサーバーを経由せずクライアントから R2 へ直接アップロードする (FR-10)。
- 一覧の API はカーソル方式のページングを提供する。
  ページサイズの既定値は 50、最大値は 200 とし、最大値を超える指定は 400 を返す。
- 想定規模は、利用者 20 人以下、1 利用者あたり店 100 件、商品 1,000 件、購入 3,000 件、抽出 30,000 件までとする。
  この規模で D1 の 1 データベースの容量上限に収まることを設計時に確認する。
- 統計の API (FR-18) は D1 の集計クエリで実装し、p95 200 ms の対象には含めない。
  統計の API の p95 は 500 ms 以内とし (2026-09-21 に所有者が決定)、成功指標の API の応答時間と同じログで測る。
  上の想定規模で全期間の集計が Workers の CPU 時間の上限に収まることを設計時に確認する。
- リリースの前に、ローカルの wrangler dev に対して k6 で VU 50 の負荷試験を実行する (ADR-0012)。
  対象は認証が不要な経路 (静的アセット 3 つとログインのチャレンジ発行) とし、失敗率 1% 未満、応答時間の p95 500 ms 未満を目安にする。
  結果 (実行日時、p95、失敗率) は記録する。
  本番の p95 の判定は Workers Logs の集計で行い、負荷試験の結果では代用しない。
  `mise run check` には含めない。

### 可用性

- Cloudflare Workers (Static Assets を含む)、D1、R2、Cloudflare Access の可用性に依存し、それ以上の可用性の仕組みは作らない。
- D1 のバックアップは D1 の Time Travel (Point-in-Time Recovery) に依存し、独自のバックアップは作らない。
  復旧できる期間は Workers Free プランで 7 日、Workers Paid プランで 30 日である (2026-09-21 に Cloudflare のドキュメントで確認。ADR-0002)。

### セキュリティ

- 認証はパスキー (WebAuthn) だけとし、パスワードを持たない。
- セッションは HttpOnly、Secure、SameSite=Lax の Cookie で保持し、トークンの生の値はデータベースに保存せずハッシュだけを保存する。
- セッションの有効期限は発行から 30 日とする。
- WebAuthn のチャレンジの有効期限は 5 分、使用は 1 回とする。
- 利用者向けの Worker の全ての API は認証を必須とする。
  例外は、登録用トークンによるパスキー登録と、ログインのチャレンジ発行と検証の API だけとする。
- 管理者 Worker の管理者画面と管理者 API は、アプリ内の認証を持たず、Cloudflare Access だけで保護する (FR-17)。
- 利用者間のデータ分離は、データベースの全クエリで利用者 ID を条件に含めることで実現する (FR-5)。
- 写真のアップロード用 URL は、有効期限 5 分、Content-Type、Content-Length を条件に含めて署名する (FR-10)。
- R2 の API トークンなどの秘密情報は Workers の Secret に置き、リポジトリに含めない。
- Frontend と Backend は同一オリジンで配信し、Backend は CORS を許可しない (ADR-0005)。
  例外として、R2 の S3 互換エンドポイントは別オリジンになるため、R2 バケットの CORS 設定でアプリのオリジンからの PUT だけを許可する (ADR-0003)。
- 状態を変更する API は `Origin` ヘッダを検証し、同一オリジン以外からの呼び出しを 403 で拒否する。
- 管理者画面と管理者 API は Worker 単位の Cloudflare Access 保護で管理者 Worker 全体を守り、所有者のメールアドレスだけを許可する (FR-17、ADR-0008)。
  管理者 Worker は Access の JWT を検証しないため、Access のポリシーを外すと管理者 API は無認証になる。
  Access の設定はデプロイ手順に含め、デプロイ後の確認タスクで有効であることを検証する。

### 運用

- Frontend のビルド成果物は Backend の Worker の Static Assets として、Backend と一緒に Cloudflare Workers にデプロイする (ADR-0005)。
  管理者 Worker は別にデプロイする (ADR-0008)。
  デプロイ手順はリポジトリの `mise.toml` のタスクで再現できる (ADR-0009)。
- データベースのスキーマ変更は wrangler の D1 マイグレーションで管理し、マイグレーションファイルをリポジトリに含める。
- ローカル開発では wrangler のローカル D1 (SQLite) とローカル R2 を使い、本番と同じスキーマとコードで動かす。
- 紐づけ前の写真のオブジェクトは `pending/` プレフィックスに置き、R2 のライフサイクルルールで 1 日後に削除する (ADR-0003)。
- ログは英語で書き、利用者の記録の内容 (商品名、感想など) をログに出さない。
- 利用者の作成と登録用トークンの発行は管理者が管理者画面で行う (FR-17)。
- CI は Backend と Frontend の全自動テストを実行する (所有者の共通規約)。
  CI は手元と同じ `mise.toml` でツールを入れ、同じタスクを実行する (ADR-0009)。

## 制約と前提

- アプリ名は brewbook とし、Flutter のパッケージ名は brew_book とする。
  Rust は 3 つのクレート (利用者向けの Worker の brew_book、管理者 Worker の brew_book_admin、共有ライブラリの brew_book_core) のワークスペースとする (ADR-0001、ADR-0010)。
- Frontend は Flutter で書く。
  Web を先行し、iOS ネイティブは同じコードからビルドできる状態を保つ (ADR-0007)。
  ルーティングは go_router、グラフは fl_chart を使い、状態管理のライブラリは追加せず Flutter 標準の ChangeNotifier と ValueNotifier で扱う。
  Web のレンダラは CanvasKit とする (ADR-0007)。
- Backend は Rust で書き、workers-rs で Cloudflare Workers 上の wasm32 として動かす (ADR-0001)。
- 依存クレートの追加は、理由を ADR または issue に記録した上で行う (ADR-0001)。
- Flutter、Rust、wrangler のバージョンはリポジトリのルートの `mise.toml` で管理し、`latest` ではなく版を固定する (ADR-0009)。
  ビルド、デプロイ、テスト、ローカル開発の起動、D1 のマイグレーション、デプロイ後の確認のコマンドラインは `mise.toml` のタスクに定義し、別のスクリプトや Makefile を置かない (ADR-0009)。
- データベースは Cloudflare D1 を使い、ローカル開発では wrangler のローカル D1 を使う (ADR-0002)。
- 写真は Cloudflare R2 に保存し、アップロード用の署名付き URL は shiguredo/s3-rs (`shiguredo_s3`) で生成する (ADR-0003)。
- 認証はパスキーだけとし、WebAuthn のサーバー側検証は外部クレートを使わず最小限を自前で実装する。
  対応アルゴリズムは ES256、attestation は none だけとする (ADR-0004)。
- Frontend と Backend は 1 つの Worker から `brewbook.<アカウントのサブドメイン>.workers.dev` で配信し、`/api/*` を Rust の処理に、それ以外を Static Assets に振り分ける (ADR-0005)。
  独自ドメインは取得しない。
- 管理者画面は別の Worker で配信し、Cloudflare Access で保護する (ADR-0008)。
- データモデルは店、商品、購入、抽出の 4 つを中心とし、抽出は購入に紐づく (ADR-0006)。
- 利用者は複数人いるが、データの共有はしない。
  利用者の作成は管理者が管理者画面で行う (FR-17)。
- オンライン前提とし、オフラインでの記録と同期は作らない。
- リポジトリは 1 つとし、Frontend と Backend を同じリポジトリの別ディレクトリに置く。
- 成果物 (コード、コメント、コミットメッセージ、ドキュメント、issue) に絵文字を使わない (所有者の共通規約)。
  コメントは日本語、ログとエラーメッセージは英語で書く (所有者の共通規約)。
- テストは次の規約と前提に従う。
  - Backend は Rust のテスト規約 (単体テストは `tests/test_<module>.rs`、PBT は `pbt/tests/prop_<module>.rs`、Fuzzing) に従う (所有者の共通規約)。
  - テストの種別は E2E、PBT、Fuzzing、形式手法、単体の 5 種とし、役割は ADR-0013 に従う。
  - WebAuthn の検証ロジックは、公開されているテストベクタを使った単体テストと、CBOR と COSE のパーサに対する PBT と Fuzzing を持つ。
  - WebAuthn のチャレンジ、登録用トークン、セッション、パスキーの状態遷移は、TLA+ の仕様と TLC のモデル検査で検証する (FR-1、FR-2、FR-3、FR-4。ADR-0013)。
  - Frontend も PBT を持ち、値の変換、統計の期間、API の入力と応答の対応を検証する (ADR-0013)。
  - Fuzzing の実行は nightly を要するため手元で行い、CI では対象の型検査を行う (ADR-0013)。
  - パスキーを伴う統合テストは、Chrome DevTools Protocol の仮想認証器で行う。
  - 有効期限などの時間に依存する検証は、設定値で短縮できるようにしてテストする。
  - Frontend は Flutter のウィジェットテストと統合テストを持つ。
  - 全ての自動テストは CI で実行し、全て通過するまでマージしない (所有者の共通規約)。

## 未確定論点

2026-09-21 に筆者が Cloudflare のドキュメントと手元の SQLite で確認し、未確定論点から外した項目は次の通りとする (出典は「## 関連資料」)。

- Workers Static Assets は 1 つの Worker で静的ファイルと `/api/*` を同じホスト名から配信でき、`run_worker_first` は `["/api/*", "!/api/docs/*"]` のようなパターンの配列を受け付け、`not_found_handling` の `single-page-application` は該当ファイルの無いパスに `index.html` を 200 で返す (ADR-0005)。
- Workers Routes はアカウントの有効なゾーンと Cloudflare でプロキシした DNS レコードが前提で、`pages.dev` には設定できない (ADR-0005)。
- Cloudflare Access は Worker 単位で有効化でき、workers.dev の URL を保護する (2026-08-14 の Cloudflare の変更履歴)。セルフホスト型アプリケーションのホスト名とパスの指定はアカウントの有効なゾーンのドメインが前提で、workers.dev のパス単位の保護はできない (ADR-0008)。
- Zero Trust の Free プランは 50 ユーザーまでで Access を含み、契約にクレジットカードの登録が必要である (ADR-0008)。
- Access の JWT は RS256 で署名され、公開鍵は `https://<チーム名>.cloudflareaccess.com/cdn-cgi/access/certs` で配布される (ADR-0008)。
- D1 Time Travel の復旧期間は Workers Free プランで 7 日、Workers Paid プランで 30 日である (ADR-0002)。
- Workers Logs の保持期間は Workers Free プランで 3 日、Workers Paid プランで 7 日で、Free プランの取り込み上限は 1 日 200,000 件である (成功指標)。
- D1 (workerd) の SQLite 関数の許可リストに `date`、`datetime`、`strftime` などの日時関数が含まれ、ISO 8601 の UTC 文字列 (末尾 `Z`、小数秒付きを含む) に `'+540 minutes'` のような分の修飾子を与えて日と月に切れることを SQLite 3.51.0 で確認した (ADR-0006)。
- `shiguredo_s3` 2026.1.0-canary.7 は、所有者が mise で入れた Rust 1.98.1 で `cargo build --target wasm32-unknown-unknown` が成功する。依存 (base64ct、crc-fast、hmac、md-5、sha1、sha2、xml と digest 系) は全て純 Rust で、OpenSSL や ring を含まない。`put_object` のビルダーに `content_type` と `content_length` を与えて `presigned` を呼ぶと、`X-Amz-SignedHeaders=content-length;content-type;host` の PUT 用 URL が得られることを手元の実行で確認した (ADR-0003)。
- リポジトリのルートの `mise.toml` が Flutter 3.47.5、Rust 1.98.1 (wasm32-unknown-unknown ターゲット付き)、wrangler 4.135.0 を固定し、`mise ls --current` でその版に解決されることを確認した (ADR-0009)。

| 論点 | 未確定の内容 | 解消の方法 |
| --- | --- | --- |
| iOS の配布形態 | 自分の端末だけか App Store 公開かが決まっていない。どの形態でもネイティブでパスキーを使うには Apple Developer Program への加入と Associated Domains の設定が必要になる。App Store 公開なら審査対応が加わる。iOS での Cookie と Bearer トークンの扱いも決まっていない (ADR-0005、ADR-0007) | 所有者は iOS の実装に着手するときに、Apple Developer Program に加入するかを決め、加入するなら配布形態 (TestFlight の内部テスト、Ad Hoc、App Store) を決める (2026-09-21 に所有者が保留を確認)。決まるまで iOS はビルドできる状態を保つだけとする。Cookie と Bearer トークンの扱いも同じ時点で決める |
| 署名付き URL の Content-Length 条件 | FR-10 は、アップロード用 URL の署名対象に Content-Type と Content-Length を含め、申告と異なるサイズの PUT を R2 が保存前に 403 で拒否することを狙う。R2 のドキュメントは Content-Type を署名対象に含めると異なる Content-Type の PUT が 403 になることを明記するが、Content-Length については触れていない (2026-09-21 に確認)。`shiguredo_s3` が Content-Length を署名対象に含めた URL を生成できることは確認済み (上の確認項目) で、未確認なのは R2 が Content-Length の不一致を拒否するかだけである | 実装者が実装の最初に、Content-Length を署名対象に含めた URL に対して申告と異なるサイズの PUT を R2 に送り、403 になることを確認する。拒否されない場合は、サイズの上限をアップロード完了後の確認 (FR-10 の完了通知) だけで強制する案を ADR-0003 の改訂として所有者に提案する |
