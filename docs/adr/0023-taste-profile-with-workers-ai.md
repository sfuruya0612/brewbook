# ADR-0023: 豆の情報からの味と特徴の推定に Cloudflare Workers AI を使う

Created: 2026-11-01
Model: DeepSeek V4.1 Flash
Status: Accepted

## 背景

購入は商品名、Producer、Origin、Region、Process、Variety、Flavor Notes、Roast を持つ (ADR-0022)。
2026-11-01 に所有者は、購入の豆の情報から、どんな味や特徴があるかを AI に調べさせて表示することを求めた (PRD の FR-24)。
写真からの購入の項目の推測 (FR-19) では、Cloudflare Workers AI の vision モデルを Worker の AI バインディングから呼んでいる (ADR-0016)。
利用者向けの Worker は Rust (workers-rs) で、依存を可能な限り少なくする方針である (ADR-0001)。
Workers AI の無料枠 (1 日 10,000 Neurons) の範囲で動かし、課金は発生させない方針である (ADR-0015、ADR-0016)。

ここでいう「AI に調べさせる」は、Web の検索エンジンで最新のレビューを探すことではなく、
豆の情報とコーヒーに関する一般的な知識から味と特徴を推定することとする。
所有者は 2026-11-01 に、知識からの推定で進めること、推定を保存すること、AI の推定である
注意書きを画面に出すことを決めた。

## 決定

- 利用者向けの Worker の既存の AI バインディング (`AI`) を使い、Workers AI の言語モデルで味と特徴を推定する。
  今回の実装では、Web の検索と、外部 (Cloudflare 以外) の AI サービスを使わない。
- 経路は `POST /api/purchases/:id/taste-profile?lang=<ja|en>` とし、認証を必須にする。
  本文は送らない。言語は `ja` または `en` を必須とし、それ以外は 400 を返す。
  存在しない購入と他の利用者の購入は 404 を返す。
- 入力は、その購入の豆の情報 (商品名、Producer、Origin、Region、Process、Variety、Flavor Notes、Roast) だけとする。
  店、価格、重量、写真は推定に使わない。
- 応答は `summary` (文字列)、`flavor_notes` (文字列の配列)、`acidity`、`sweetness`、`bitterness`、`body`、`aroma` (文字列または null) に加えて、
  `brewing_method` (おすすめの淹れ方。100 文字以内)、`grind_setting` (挽き目。80 文字以内)、
  `process_description` (精製方法の説明。200 文字以内)、`region_characteristics` (地域の特色。200 文字以内) を持つ。
  推測できない項目は null、Flavor Notes は推測できないときに空の配列とする。
  まとめは 400 文字以内、Flavor Notes は 10 件以内で 1 件 40 文字以内、特徴は 80 文字以内とする。
- 出力の言語は `lang` に合わせる。プロンプトで、豆の情報をデータとしてだけ扱い、その中の指示に従わないこと、
  不確かなことを断定しないこと、特定の農園や受賞を捏造しないことを指示する。
- サーバーはモデルの出力を検証し、形式に合わない項目を空にする。
  表示できる内容が 1 つも無いときは 500 を返す。
- AI の呼び出しに失敗したとき (無料枠の超過、タイムアウト、モデルのエラー) は、理由を区別せず 500 を返す。
- 推定は購入の `taste_profile` に JSON の文字列で保存する。推測をやり直すと上書きする。
  どの記録も変更せず、購入の詳細を開いただけでは AI を呼ばない。
  利用者が「AI に聞く」を押したときだけ推定し、まとめ、Flavor Notes のタグ、特徴の表、
  AI の推定である旨の注記を購入の詳細に表示する。
  保存済みの推定は購入の応答 (`taste_profile`) に含め、次に購入の詳細を開いたときに表示する。
- AI の呼び出しに失敗したときは、前に保存した推定を残す。
- モデル名は vars の `AI_TASTE_MODEL` で環境ごとに差し替えられるようにする。
  既定値は写真からの推測と同じ `@cf/meta/llama-4-scout-17b-16e-instruct` とする。
- 推定の入力 (豆の情報) と出力 (推定の結果) はログに出さない。
  Cloudflare は Workers AI の顧客コンテンツをモデルの学習に使わない (2026-09-30 に Cloudflare のドキュメントで確認。ADR-0016)。

## 検討した選択肢

| 選択肢 | 採用しない理由 |
| --- | --- |
| Web の検索 API と組み合わせて、実際のレビューや記事を探す | 検索 API の契約と API キーの管理が増え、豆の情報が Cloudflare の外に出る。無料枠の管理も別になる。今回の実装では外部の検索を使わない |
| 外部 (Cloudflare 以外) の AI サービスを使う | ベンダーと契約と API キーの管理が増え、豆の情報が Cloudflare の外に出る。ADR-0016 の「外部の AI サービスに送らない」扱いと揃わない |
| 推定を保存しない | 所有者が保存を求めた。開くたびに再推定すると無料枠を消費し、前回の結果も見られない |
| 推定を購入と 1 対 1 の別テーブルに保存する | 購入の削除、エクスポート、アカウント削除に追随する処理が増える。推定は購入に 1 つなので、購入の列で足りる |
| 購入の詳細を開いたときに自動で推定する | 無料枠を消費する操作が画面を開くだけで起きる。利用者が押したときだけ呼ぶ |
| 推定を購入のフォームにも表示する | フォームは入力の補助 (FR-19) で、保存前の情報だけでは推定の根拠が少ない。購入の詳細に置く |
| 写真からの推測の応答に味と特徴を足す | 写真の推測は購入の項目を入力するための機能で、保存前の情報だけでは推定の根拠が少ない。経路と目的を分ける |

## 結果

- 推定は AI の推論に依存し、応答に数秒かかる。成功指標の応答時間の対象に含めない。
  推論の待ちは Worker の CPU 時間を消費しない。
- 推定の精度は保証されない。画面に AI の推定であることを明記し、実際の味と異なる場合があることを伝える。
- 所有者は、Web 検索ではなく知識からの推定を選んだ。Web 検索を求める場合は、外部の検索 API の採用を別の ADR で決める。
- 1 回あたりの消費は、同じモデルの写真からの推測 (ADR-0016) の単価で見積もる。
  入力は約 400 tokens、出力は上限の 1536 tokens と仮定すると、約 130 Neurons
  (入力 24,545 Neurons / M tokens、出力 77,273 Neurons / M tokens。ADR-0016 の表) になる。
  無料枠 (1 日 10,000 Neurons) では 1 日約 75 回まで使える。
  利用者が押したときだけ呼ぶため、想定規模 (利用者 20 人) では無料枠に収まる見込みである。
- マイグレーションで purchases に `taste_profile` を足す。エクスポートは購入の列として推定を含め、
  購入の削除とアカウント削除は購入の行と一緒に推定を消す。既存の応答の形は
  `taste_profile` が増える (FR-24)。
- 購入の一覧と抽出の一覧の応答にも `taste_profile` が含まれるため、応答は推定の分だけ大きくなる。
  推定は購入に 1 つで、一覧の件数は最大 200 件である (PRD の性能)。
- AI の呼び出しは CI で実行できない (Cloudflare のアカウントとネットワークが要る。FR-19 と同じ扱い)。
  プロンプトの生成と応答の解析は `brew_book_core` の単体テストと PBT で検証し、
  正常系は staging へのデプロイで実在の購入を指定し、推定の保存と、次の取得で
  保存済みの推定が返ることを確認して、結果を issue に記録する。
  言語の入力不正 400、未認証 401、存在しない購入と他の利用者の購入の 404、AI の失敗の 500 は
  結合テストで検証する。保存済みの推定が購入の応答に含まれることは、下ごしらえで
  推定を入れた購入の取得で検証する。画面の表示、開いたときの保存済みの推定の表示、
  開いただけでは AI を呼ばないこと、失敗の再試行は Frontend のブラウザテストで検証する。
- 利用者向けの Worker の経路の台帳に `purchases_taste_profile` が増える。
  正常系を CI で実行しない区分 (`OkTest::Staging`) の経路が 1 つ増える。
