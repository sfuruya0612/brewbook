# ADR-0008: 管理者画面を別の Worker に置き、Cloudflare Access で保護する

Created: 2026-09-21
Model: Claude Fable 5.1
Status: Accepted
改訂: 2026-10-02 (issue 0045。Frontend を Dioxus の Web だけにする決定 (ADR-0017) に合わせて、Flutter の記述を Web だけの対象に改めた)

## 背景

利用者の作成と登録用トークンの発行 (PRD の FR-17) は、初版では Backend のクレートに含む CLI で行う案を置いていた (ADR-0001 の初版)。
2026-09-21 に所有者が、管理者用の Web 画面を作ることと、無料枠に収まるなら Cloudflare Access で保護することを決めた。

利用者向けの Worker は workers.dev のホスト名で配信する (ADR-0005)。
筆者は、workers.dev のホスト名では Access をパス単位で掛けられないという理解を所有者に伝え、2026-09-21 に Cloudflare のドキュメントで次を確認した。

- Access は Worker 単位で有効化でき (Workers のダッシュボードの Access タブ、または `worker` 種別のセルフホスト型アプリケーション)、その Worker の workers.dev の URL、プレビュー URL、カスタムドメインを全て保護する (2026-08-14 の変更履歴)。
- ホスト名とパスを指定するセルフホスト型アプリケーションは、アカウントの有効なゾーンのドメインが前提である。
  workers.dev のホスト名にはパス単位の保護は無い。

利用者向けの Worker 全体を Access で保護すると利用者もログインできなくなるため、管理者画面を別の Worker に分ける。

Access は認証したリクエストに JWT (`Cf-Access-Jwt-Assertion` ヘッダ) を付ける。
この JWT は RS256 で署名され、公開鍵は `https://<チーム名>.cloudflareaccess.com/cdn-cgi/access/certs` で配布される (2026-09-21 にドキュメントで確認)。
Worker で検証するには `rsa` クレート相当の依存が増えるため、所有者は依存を増やさないことを優先して JWT を検証しないことを決めた。

## 決定

- 管理者画面は利用者向けの Worker とは別の Worker (管理者 Worker、ADR-0001 のワークスペースの coffee_log_admin) で実装し、`coffee-log-admin.<アカウントのサブドメイン>.workers.dev` で配信する。
- 管理者 Worker に Worker 単位の Cloudflare Access 保護を設定し、ポリシーで所有者のメールアドレスだけを許可する。
  認証には Access の One-time PIN (メール) を使う。
  利用者向けの Worker には Access を設定せず、アカウント全体の Worker を既定で保護する設定も使わない。
- 管理者 Worker は Access の JWT を検証しない。
  管理者 Worker の安全性は Access の設定だけに依存する。
- 管理者画面は管理者 Worker がサーバー側で生成する HTML のフォームで作り、JavaScript を使わない。
  機能は、利用者の一覧、利用者の作成 (表示名の入力)、登録用トークンの発行の 3 つとする。
  フォームの送信先の経路を管理者 API と呼び、アプリ内の認証を持たない。
- 登録用トークンの発行結果 (利用者向けの Worker のホスト名を含む登録用リンク) は、発行直後のレスポンスに 1 回だけ含め、再表示できない。
  利用者向けの Worker のホスト名は管理者 Worker の環境変数で持つ。
- 管理者 Worker は利用者向けの Worker と同じ D1 データベースをバインディングで参照する (ADR-0002)。
  users テーブルと registration_tokens テーブルを読み書きし、passkey_credentials テーブルを読む。
  それ以外のテーブルは扱わない。
- 状態を変更するフォームの送信は、`Origin` ヘッダが管理者 Worker のオリジンと一致しない場合に 403 で拒否する (ADR-0005 と同じ規則)。
- Access の設定はデプロイ手順に含める。
  デプロイ後の確認タスク (mise のタスク。ADR-0009) で、認証なしで管理者画面の URL を取得すると Access のログイン画面へリダイレクトされる (302) ことを検証し、そうでなければ失敗させる。
- Zero Trust の Free プラン (50 ユーザーまで。Access を含む。契約にクレジットカードの登録が必要) を使う (2026-09-21 に Cloudflare のプランのページで確認)。

## 検討した選択肢

| 選択肢 | 採用しない理由 |
| --- | --- |
| 管理者用の CLI (初版の案) | 所有者が Web 画面を選んだ |
| 利用者向けの Worker の `/admin/*` を Access で保護する | パスを指定するセルフホスト型アプリケーションはアカウントの有効なゾーンのドメインが前提で、workers.dev には Worker 単位の保護しか無い (2026-09-21 に確認)。独自ドメインを取れば可能だが、所有者が独自ドメインを取らないことを選んだ |
| 管理者画面を利用者向けの Frontend (Dioxus) で作る | 利用者向けのアプリと管理者画面が同じ成果物になり、管理者用の経路がアプリに混ざる。3 機能のフォームには過剰 |
| 管理者画面をアプリ内の管理者ロールで作る | パスキーで認証する管理者ロールをアプリに持つことになり、認可の分岐が全 API に増える |
| Access の JWT を Worker で検証する | RS256 の検証のために `rsa` クレート相当の依存が増える。所有者が検証しないことを選んだ |
| `ctx.access` で利用者情報を読む | Workers のランタイムは Access で認証した利用者のメールアドレスなどを `ctx.access.getIdentity()` で JWT の検証なしに返す。workers-rs 0.8.6 の `Context` にはこの API のラッパーが無く、JS 相互運用が要る。管理者は 1 人で利用者情報を使う要求が無いため採用しないが、2026-09-21 に所有者が使わないことを決めた。監査ログにメールアドレスを残す要求が出たときに本 ADR の改訂として再検討する |
| Basic 認証を Worker で実装する | パスワードの管理が必要になる。Access の方が管理者側の実装が無い |

## 結果

- Access のポリシーを外すか誤って設定すると、管理者画面と管理者 API は無認証で公開される。
  確認タスクがこれを検出する。
  管理者 Worker は利用者のデータ (shops、products、purchases、brews と R2) には触れないため、影響は利用者の作成とトークンの発行に限られる。
- Access の JWT を検証しないため、管理者 Worker に Access を迂回して到達できる経路が Cloudflare 側に存在しないことに依存する。
  Worker 単位の保護は、その Worker のどの URL からの到達も保護するとドキュメントに書かれている。
- ローカル開発では、wrangler の設定の `access.dev` ブロックで Access の認証済みの状態を模擬できる。
  管理者 Worker は識別情報を使わないため、この設定は使わない。
- 管理者 Worker の HTML は Rust の文字列テンプレートで生成し、テンプレートエンジンのクレートは追加しない。
  利用者の表示名は HTML エスケープして出力する。
- 管理者 Worker の自動テストは、HTML 生成とフォームの入力検証を純粋な関数として単体テストし、D1 を触る部分は `wrangler dev` に対する結合テストで検証する。
- Worker 単位の Access 保護が使えないと分かった場合は、独自ドメインを取得して `/admin/*` をパスで保護する案を本 ADR の改訂として所有者に提案する。
