# ADR-0020: 記録の削除 (物理削除と連鎖削除)

Created: 2026-10-08
Model: DeepSeek V4.1 Flash
Status: Accepted

## 背景

2026-10-08 に所有者が、登録した記録 (店、商品、購入、抽出) を削除できるようにし、各項目の詳細に
削除ボタンを置きたいと求めた。PRD に FR-23 を追加する。

ADR-0006 は「アカウント削除 (FR-15) だけは物理削除とし、利用者に属する全行と R2 の全オブジェクトを
削除する」と定め、検討した選択肢でカスケード削除を「子の記録が黙って消える」として採らなかった。
ADR-0018 はアーカイブ (論理削除) を廃止し、廃止の検討では「新しい削除の API と画面は要求に無い」と
して記録の物理削除の機能を作らなかった。
今回は所有者が記録の削除の機能を要求したため、削除の意味と参照の扱いを決める必要がある。

記録の参照は、購入が商品 (必須) と店 (任意) を、抽出が購入 (必須) を参照する。
商品は Flavor Notes のタグとの対応 (`product_flavor_tags`) を持ち、購入の写真は R2 の
オブジェクトである (ADR-0003)。
外部キー制約を有効にしているため、親を消す前に子の行を消す必要がある (ADR-0006)。

## 決定

- 店、商品、購入、抽出の 4 つの記録を物理削除できるようにする。
- 削除の API は `DELETE /api/shops/:id`、`DELETE /api/products/:id`、
  `DELETE /api/purchases/:id`、`DELETE /api/brews/:id` の 4 経路とし、認証を必須にする。
  成功は 204 を返し、存在しない ID と他の利用者の ID は 404 にする (ADR-0006 の規則を変えない)。
- 参照があるときは連鎖削除にする。
  - 店: 購入の `shop_id` を NULL にして購入は残す (店は購入にとって任意の項目のため)。
    店の指定を外した購入の `updated_at` は現在時刻にする (行の内容が変わるため。ADR-0006)。
  - 商品: その商品の購入、購入に紐づく抽出、購入の写真 (R2)、商品の Flavor Notes の対応
    (`product_flavor_tags`) を削除する。タグの行 (`flavor_tags`) は残す (ADR-0006)。
  - 購入: その購入の抽出、購入の写真 (R2) を削除する。
  - 抽出: 他から参照されないため、行の削除だけを行う。
- 子の行は 1 つの D1 の batch で、外部キーの参照元から先に削除する (ADR-0002、ADR-0006)。
  R2 のオブジェクトは D1 の前に消す。R2 の削除に失敗した場合は記録が残ったままになり、
  利用者が同じセッションで再試行できる (アカウント削除と同じ順序)。
- 削除の影響の件数 (消える購入と抽出の件数、店の指定が外れる購入の件数) を返す経路
  (`GET /api/<記録>/:id/delete-impact`) を足し、画面は確認ダイアログに件数を出す。
  連鎖で消える記録の件数を事前に示すため、ADR-0006 がカスケード削除を採らなかった理由
  (子の記録が黙って消える) は解消する。
- 削除の操作は画面のヘッダーに置き、確認ダイアログを経て行う (FR-15 と同じ)。
  削除は元に戻せないため、確認の前に削除の API を呼ばない。
- 本 ADR は、ADR-0006 の「物理削除はアカウント削除だけ」の決定と、検討した選択肢の
  「カスケード削除 (子の記録が黙って消える)」の却下を部分置き換えにする。
  データモデルの他の決定 (4 つの記録の関係、`user_id` を全クエリの条件に含める規則など) は残る。

## 検討した選択肢

| 選択肢 | 採用しない理由 |
| --- | --- |
| 参照があるときは 409 で拒否する | 使い切った豆や閉店した店を消すのに、子の記録を先に全部消す手間が要る (ADR-0006 が「参照されている親の削除を拒否する」を採らなかったのと同じ理由) |
| 論理削除 (アーカイブ) にする | アーカイブは ADR-0018 で画面、API、データベースから廃止済みである |
| 店の削除で購入も削除する | 店は購入の任意の項目である。店を消しただけで購入の履歴を失うのは過剰である |
| 削除の影響の件数を出さない | 商品の削除では多数の購入と抽出が消え得る。消える件数を事前に見せないと取り返しがつかない |
| 削除の操作を本文の下のボタンにする | 所有者がヘッダーの操作を選んだ。記録ごとの操作 (お気に入り、編集、保存) と同じ場所にまとまる |

## 結果

- 削除の 4 経路と削除の影響の 3 経路が台帳に増え、結合テストのスイートが更新される (0056)。
- 削除の SQL は子から順に消す。R2 の削除は複数キーの削除 (`Bucket::delete_multiple`。1 回に
  最大 1,000 キー) を使い、商品の削除で写真が想定規模の 3,000 件でも呼び出しは 3 回に収まる。
- 画面は削除の確認に連鎖で消える件数を出し、削除の後は一覧に戻って「削除しました。」を知らせる。
- PRD に FR-23 を足し、FR-5、スコープ、ユースケース、目的、背景、関連資料を更新する。
- ADR-0006 の Status と本文冒頭の注記を、ADR-0018 と本 ADR の両方を指すように更新する。
