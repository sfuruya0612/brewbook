# ADR-0007: Frontend を Flutter で書き、Web を先行して iOS を後にする

Created: 2026-09-21
Model: Claude Fable 5.1
Status: Accepted

## 背景

所有者は、Frontend を Flutter で書き、まず Web アプリケーションとして動かし、後に iOS 向けにビルドしたネイティブアプリとしても動かすことを求めた。
iOS の配布形態 (自分の端末だけか App Store 公開か) は未定である。
UI は日本語と英語の両方に対応し、オフラインでの記録と同期は作らない。
2026-09-21 に所有者が、統計とグラフを初回スコープに入れること、CI での iOS のビルドをやめること、項目名を日本語 UI では日本語で表示することを決めた。

## 決定

- Frontend は Flutter で書き、1 つのコードベースから Web と iOS をビルドする。
- Web を先行する。
  Flutter Web のビルド成果物は Backend の Worker の Static Assets として配信する (ADR-0005)。
- iOS はビルドできる状態を保つが、CI では iOS のビルドを実行しない。
  プラットフォーム固有のコードはインターフェースの後ろに置き、iOS 対応時にビルドを確認する。
  配布形態が決まるまで配布しない。
  iOS 固有の機能 (パスキーのネイティブ連携、Associated Domains) は、配布形態が決まってから実装する。
- Flutter の版はリポジトリのルートの `mise.toml` で固定し、ビルドとテストのコマンドラインは mise のタスクに定義する (ADR-0009)。
- ルーティングは go_router を使う。
  状態管理のライブラリは追加せず、Flutter 標準の ChangeNotifier と ValueNotifier で扱う (2026-09-21 に所有者が依存最小の案を選んだ)。
- UI の文言は Flutter の l10n (ARB ファイル) で日本語と英語を持ち、コードに直書きしない。
  項目名は日本語 UI では日本語の訳語 (PRD の FR-16) で表示する。
- 統計のグラフ (PRD の FR-18) は Frontend で描画する。
  集計は Backend の API が行い、Frontend は集計結果を受け取って描くだけにする。
  グラフ描画は fl_chart を使い、他のグラフライブラリは追加しない (2026-09-21 に所有者が決定)。
- 写真の JPEG 変換と縮小はクライアントで行う (ADR-0003)。
  Web では Canvas API、iOS ではネイティブの画像処理を使い、プラットフォームごとの実装を 1 つのインターフェースの後ろに置く。
- パスキーは、Web では `navigator.credentials` を JS 相互運用で呼び、iOS では配布形態の決定後にネイティブの API を使う。
- オフライン対応は作らない。
  ネットワークエラーは、利用者に再試行を促す表示で扱う。

## 検討した選択肢

| 選択肢 | 採用しない理由 |
| --- | --- |
| Web と iOS で別の技術を使う | 所有者が Flutter で 1 つのコードベースにすることを求めた |
| iOS を先行する | 配布形態が未定で、Apple Developer Program への加入も未確認。Web なら配布の障壁が無い |
| PWA として iOS に対応する | iOS の PWA はパスキーと写真の扱いに制約がある。所有者がネイティブビルドを求めた |
| オフライン対応 | 端末側の DB と同期が必要になり、設計が大幅に複雑になる。所有者がオンライン前提を選んだ |

## 結果

- Flutter Web のレンダラは CanvasKit とする (2026-09-21 に所有者が決定)。
  初回ロードのサイズは Static Assets での配信で測り、問題があれば skwasm への変更を本 ADR の改訂として提案する。
- Web と iOS で挙動が分かれる部分 (パスキー、写真の変換、ファイルの保存) はインターフェースで抽象化し、Web の実装を先に作る。
- Web で復号できる画像形式はブラウザに依存する。
  HEIC の変換は iOS ネイティブの対応時に扱う。
- 同一オリジン (ADR-0005) のため、Web ではセッション Cookie をブラウザが管理する。
  iOS では、ネイティブの HTTP クライアントの Cookie 管理を使うか Bearer トークンを併用するかを、iOS 対応時に決める (PRD の未確定論点)。
- ウィジェットテストと統合テストを持ち、画面数 (PRD の成功指標) を統合テストで検証する。
- iOS のビルドは CI で検証しないため、iOS 対応時にビルドが壊れている可能性がある。
  所有者はこれを受け入れた。
