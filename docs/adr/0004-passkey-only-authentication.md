# ADR-0004: 認証をパスキーだけにし、WebAuthn の検証を自前で最小実装する

Created: 2026-09-21
Model: Claude Fable 5.1
Status: Accepted

## 背景

アプリは複数の利用者が個人アカウントで使う (PRD の「ユーザーとユースケース」)。
所有者は、認証手段をパスキー (WebAuthn) だけにし、パスワードとメールリンクを持たないことを決めた。
利用者の作成は管理者が管理者画面 (ADR-0008) で行い、セルフサインアップは無い。
所有者は、複数のパスキーの追加、名前付け、削除 (最後の 1 つは削除不可) を初回スコープに含めることを確認した。

Rust の WebAuthn ライブラリとして広く使われている webauthn-rs は、既定で OpenSSL に依存しており、wasm32-unknown-unknown (ADR-0001) ではビルドできない見込みである。
wasm で使える構成があるかは検証していない。
所有者は、対応範囲を絞った上で検証ロジックを自前で実装することを選んだ。

## 決定

### 認証の方式

- 認証はパスキーだけとする。
  パスワード、メールリンク、外部 IdP は持たない。
- Relying Party ID は本番のホスト名 `coffee-log.<アカウントのサブドメイン>.workers.dev` (ADR-0005) とする。
- 登録では `attestation: none` を要求し、attestation statement は検証しない (認証器の種類を制限しない)。
- 公開鍵のアルゴリズムは ES256 (COSE alg -7) だけを受け付ける。
  2026-09-21 に所有者が ES256 だけで進めることを確認した。
- 登録時に `residentKey: preferred`、`userVerification: required` を要求し、ログイン時も `userVerification: required` とする。
- チャレンジは 32 バイトの乱数で、D1 に保存し、有効期限は 5 分、使用は 1 回とする。
- 署名カウンタは W3C WebAuthn Level 3 の 7.2 節に従って検証する。
  保存値と今回の値の両方が 0 のときは検査を省略する。
  どちらかが 0 でないとき、今回の値が保存値以下ならログインを拒否し (409)、大きければ保存値を更新する。
- 1 利用者は複数のパスキーを持てる。
  各パスキーは 1 文字以上 50 文字以下の名前を持ち、名前は後から変更でき、最後の 1 つは削除できない。
  名前の長さの範囲と名前の変更は筆者が置き、2026-09-21 に所有者が承認した。

### 利用者の作成と登録用トークン

- 管理者は、利用者の行と、有効期限 24 時間の登録用トークンを管理者画面 (ADR-0008) で作成する。
  データベースにはトークンのハッシュだけを保存する。
- 利用者は、トークンを含む URL (`/register?token=<トークン>`) を開いてパスキーを登録する。
  登録が成功したらトークンを使用済みにし、セッションを発行する。
- 登録用トークンは既存の利用者にも発行できる。
  そのトークンで登録したパスキーは既存の利用者に追加される。
  パスキーを全て失った利用者の救済はこの経路で行う (PRD の UC-14)。
- ログイン済みの利用者は、トークンなしでパスキーを追加できる (PRD の FR-3)。

### セッション

- セッションは 32 バイトの乱数トークンとし、D1 にはハッシュだけを保存する。
- セッションは HttpOnly、Secure、SameSite=Lax の Cookie でクライアントに渡す。
  有効期限は発行から 30 日とする。
- ログアウトとアカウント削除でセッションの行を物理削除する。

### 実装

- WebAuthn の検証は、外部の WebAuthn クレートを使わず自前で実装する。
  実装範囲は次に限定する。
  - `clientDataJSON` の type、challenge、origin の検証
  - `authenticatorData` の rpIdHash、flags (UP、UV)、signCount の検証
  - attestation object の CBOR デコードと、`fmt: none` の受け入れ、COSE キー (EC2、P-256) の取り出し
  - ES256 の署名検証
- 暗号は RustCrypto の `p256` (ecdsa feature) と `sha2` を使う。
  CBOR のデコードは、WebAuthn が使う範囲 (map、bytes、text、integer、array) だけを自前で実装する。
- 検証ロジックはバインディングに依存しない純粋な関数として書き、公開されているテストベクタを使った単体テストと、CBOR と COSE のパーサに対する PBT と Fuzzing を持つ (PRD の「制約と前提」)。

## 検討した選択肢

| 選択肢 | 採用しない理由 |
| --- | --- |
| メールリンク認証 | メール送信サービスが必要になり、依存と運用が増える |
| パスワード | 漏洩とフィッシングの対策が必要になる。パスキーで置き換えられる |
| 利用者の認証に Cloudflare Access を使う | Worker の前段で守れるが、利用者ごとのデータ分離をアプリで持てない。所有者がアプリ内の認証を選んだ。管理者画面だけは Access で守る (ADR-0008) |
| webauthn-rs | OpenSSL 依存で wasm32 ではビルドできない見込み。所有者が自前実装を選んだ |
| ES256 に加えて RS256 を受け付ける | `rsa` クレートが増える。所有者が ES256 だけを選んだ (2026-09-21 に再確認) |
| 署名カウンタが保存値以下なら常に拒否する | 署名カウンタを常に 0 で返す認証器 (同期パスキー) で 2 回目以降のログインが必ず失敗する |
| セルフサインアップ | 不特定多数の登録と R2 の乱用を防ぐため、所有者が管理者による作成を選んだ |

## 結果

- WebAuthn の検証を自前で実装するため、仕様 (W3C WebAuthn Level 3) への準拠とテストの厚さが安全性を決める。
  実装には仕様の該当節を引用したコメントを付ける。
- RS256 だけを出す認証器では登録できない。
  所有者はこの制約を受け入れた。
- Web の Frontend (Dioxus) では `navigator.credentials` を `web-sys` 経由で呼ぶ。
  iOS ネイティブは対象にしない (ADR-0017)。
- Relying Party ID を後から変えると、登録済みのパスキーは全て無効になる。
  後で独自ドメインに移す場合は、全利用者が登録用トークンで再登録する (ADR-0005)。
- パスキーを伴う統合テストは、Chrome DevTools Protocol の仮想認証器で行う。
