# ADR-0002: データベースに Cloudflare D1 を使う

Created: 2026-09-21
Model: Claude Fable 5.1
Status: Accepted

## 背景

所有者は当初から「Database SQLite」と「Backend は Workers と D1」を挙げていた。
D1 は Cloudflare が提供する SQLite ベースのデータベースで、Workers のバインディングから使う。
Backend を Rust (workers-rs) に変更した後も (ADR-0001)、D1 は `worker` クレートの `d1` feature から使える。

## 決定

- 本番のデータベースは Cloudflare D1 とする。
- ローカル開発と結合テストでは、`wrangler dev` が提供するローカルの D1 (SQLite ファイル) を使い、本番と同じスキーマとコードで動かす。
- D1 データベースは 1 つとし、利用者向けの Worker と管理者 Worker (ADR-0008) の両方が同じデータベースをバインディングで参照する。
  マイグレーションは利用者向けの Worker の設定から実行し、管理者 Worker はマイグレーションを持たない。
- スキーマ変更は wrangler の D1 マイグレーション (`migrations/` 以下の SQL ファイル) で管理し、リポジトリに含める。
- SQL は ORM を使わず、`worker` クレートの D1 API にプレースホルダ付きの SQL を直接渡す。
- users を除く全てのテーブルに利用者 ID の列を持ち、全てのクエリで利用者 ID を条件に含める (PRD の FR-5)。
  例外は ADR-0006 に記す webauthn_challenges のログイン用の行だけとする。
- 主キーはサーバーで生成する UUID v4 の文字列とする。
- 日時 (抽出日時、作成日時、有効期限など) は ISO 8601 の UTC の文字列で保存する。
- 日付 (購入日、Roast Date) はタイムゾーンを持たない `YYYY-MM-DD` の文字列で保存する。
  クライアントが端末のタイムゾーンで決めた日付をそのまま保存し、サーバーは変換しない。
- 一覧のページングはカーソル方式とする。
  カーソルは並び順のキー (日時または日付と ID) を符号化した文字列とする。
- バックアップは D1 の Time Travel (Point-in-Time Recovery) に依存し、独自のバックアップは作らない。
  復旧できる期間は Workers Free プランで 7 日、Workers Paid プランで 30 日である (2026-09-21 に Cloudflare のドキュメントで確認)。

## 検討した選択肢

| 選択肢 | 採用しない理由 |
| --- | --- |
| Durable Objects の SQLite ストレージ | 利用者ごとに 1 オブジェクトを持つ設計は可能だが、横断的な運用 (マイグレーション、管理者の SQL 実行) が D1 より煩雑になる |
| 外部のマネージド DB (Postgres など) | Cloudflare 構成から外れ、接続の秘密情報と接続数の管理が必要になる |
| ORM やクエリビルダ (sqlx、sea-query など) | D1 のバインディングは wasm 経由の独自 API であり、これらのクレートは D1 に対応していない。依存を増やさない方針にも反する |
| オフセット方式のページング | 抽出の一覧は日時の降順で、新しい行の追加で位置がずれる。カーソル方式ならずれない |

## 結果

- D1 の制約 (1 データベースあたりの容量上限、1 クエリの行数上限、トランザクションは batch API の範囲) を設計で考慮する。
  PRD の想定規模 (利用者 20 人以下、1 利用者あたり抽出 30,000 件まで) が容量上限に収まることを設計時に確認する。
- 複数の文を 1 つのトランザクションで実行するには D1 の batch を使う。
  アカウント削除 (PRD の FR-15) は batch で行う。
- D1 の API は wasm 経由でしか呼べないため、SQL の組み立てと結果の変換は、ネイティブターゲットで単体テストできるようにバインディングに触るコードから分離する。
