# 購入の写真の署名付きアップロードと取得を実装する

Created: 2026-09-21
Model: deepseek-v4p1-flash
対応 ADR: ADR-0003 (docs/adr/0003-photo-storage-r2-presigned-upload.md)
関連 PRD: FR-5、FR-10、未確定論点 (署名付き URL の Content-Length 条件)、セキュリティ (署名付き URL の条件)、やらないこと (複数枚の写真、サーバー側の変換)
依存: 0001, 0002, 0003, 0005, 0007

## 背景

ADR-0003 は、購入のパッケージ写真を Cloudflare R2 に保存し、クライアントが署名付き PUT URL で直接アップロードすると決めた。
署名は `shiguredo_s3` で生成し、Content-Type (`image/jpeg`) と Content-Length (申告サイズ) を署名の対象に含め、有効期限を 5 分とする。
アップロード完了の通知を受けた Backend は、R2 バインディングで `pending/` のオブジェクトの存在、サイズ、Content-Type を確認してから `users/<利用者 ID>/purchases/<購入 ID>/<UUID>.jpg` に移し、購入に紐づける。
PRD の未確定論点は、R2 が Content-Length の不一致を拒否するかを実装の最初に検証することを求める。
0007 で購入の API ができ、`photo_key` 列だけがある。本 issue がアップロードと取得を追加する。

## 目的

利用者が購入にパッケージ写真を 1 枚添付し、差し替え、削除でき、認証済みの利用者だけが写真を取得できるようにする。

## 設計判断

### 最初に行う検証

- 実装の最初に、Content-Length を署名の対象に含めた URL に対して申告と異なるサイズの PUT を R2 に送り、403 で拒否されるかを確認する。
  拒否されない場合は、サイズの上限を完了通知の確認だけで強制する案を ADR-0003 の改訂として所有者に提案し、提案の結果を issue 本文に追記する。
- ローカルの R2 が S3 互換の HTTP エンドポイントを提供するかを確認する。
  提供しない場合は、期限切れの URL の拒否を開発用の R2 バケットへの実リクエストで確認し、その判断と結果を issue 本文に追記する (CI では実行しない。ネットワークと資格情報が要るため)。

### 経路の一覧

| 操作 | 経路 |
| --- | --- |
| アップロード用 URL の発行 | `POST /api/purchases/<購入 ID>/photo/upload-url` (申告サイズを受け取る) |
| アップロード完了の通知 | `POST /api/purchases/<購入 ID>/photo` (発行時に返したオブジェクトキーを受け取る) |
| 写真の取得 | `GET /api/purchases/<購入 ID>/photo` |
| 写真の削除 | `DELETE /api/purchases/<購入 ID>/photo` |

- 4 つの経路は購入 ID を取り、存在しないか他の利用者の購入は 404 を返す (FR-5)。
- 取得は R2 バインディングで読み出して `image/jpeg` で返す (ADR-0003)。
  写真が無い購入は 404 を返す。
  PRD の 404 の定義は記録とトークンに限るが、購入に写真が紐づいていない場合も資源が無いものとして 404 にする。
- 取得の応答には `Cache-Control: private, no-store` を付ける (共用の端末でログアウト後にキャッシュから写真が見えないようにする。UC-12)。
- 写真は 1 購入につき 1 枚とし、サーバー側の変換と縮小は行わない (PRD のやらないこと)。

### アップロード

- 申告サイズが 5 MB (5,000,000 バイト) を超える場合は 400 を返し、URL を発行しない。
- `shiguredo_s3` を `=2026.1.0-canary.7` で固定し、既定の feature (`rust-crypto`) を使う (`aws_lc_rs` は有効にしない)。
  wasm32-unknown-unknown でビルドできることは 2026-09-21 に確認済みである (ADR-0003)。
  ビルドできなくなった場合だけ、署名付き URL の生成を自前で実装する代替案 (所有者が承認済み) に切り替える。
- 署名付き PUT URL は、Content-Type を `image/jpeg`、Content-Length を申告サイズ、有効期限を設定値 (既定 300 秒) として生成する。
- 返すオブジェクトキーは `pending/<利用者 ID>/<UUID>.jpg` とし、URL と一緒に返す。
- 完了通知では、受け取ったキーが `pending/<その利用者 ID>/<UUID>.jpg` の形式に一致することを検査する (利用者 ID の後の部分が 16 進とハイフンだけの UUID であることまで見る)。
  一致しない場合は 400 を返し、オブジェクトに触れない。
  キーはクライアントから戻される信頼できない入力であり、他の利用者の `pending/` のオブジェクトを取り込めないようにするためである。
  R2 バインディングで `pending/` のオブジェクトの存在、サイズ (申告サイズと一致して 5 MB 以下)、Content-Type を確認する。
  確認に失敗した場合はオブジェクトを削除して 400 を返し、購入に紐づけない。
- 確認に成功したら、オブジェクトを取得して `users/<利用者 ID>/purchases/<購入 ID>/<UUID>.jpg` に保存し、`pending/` のオブジェクトを削除し、購入の `photo_key` を更新する。
  R2 バインディングには複製と移動の操作が無いため、取得と保存の 2 操作で行う (ADR-0003)。
  写真は 5 MB 以下なので Worker のメモリに収まる。
- 差し替えは、既に写真がある購入に対して URL の発行と完了の通知を行うことで実現する。
  紐づけが成功した後で古いオブジェクトを削除する。
- 削除では、購入の `photo_key` を NULL にしてからオブジェクトを削除する。
- 有効期限の秒数は環境変数 (設定値) とし、テストでは短い値を注入する。
  期限の判定は R2 が行い、Backend は関与しない (FR-10)。
  署名に含まれる有効期限の値 (`X-Amz-Expires`) が設定値と一致することを単体テストで確認する。
- 採らない案: Worker 経由でアップロードする (Worker の CPU 時間と帯域を使う。ADR-0003)、取得も署名付き GET URL にする (URL を知る者が認証なしで取得できる。ADR-0003)、完了通知の確認を省く (申告と異なるサイズのオブジェクトが紐づく)。

### 設定と運用

- `backend/coffee_log/wrangler.toml` に R2 バケットのバインディング (`PHOTOS`) を追加し、バケット名は `coffee-log-photos` とする。
- R2 の API トークン (アクセスキーとシークレット) は Workers の Secret に置き、リポジトリに含めない。
  バケット名と S3 互換のエンドポイントは vars に置く。
  開発では開発用のバケットと API トークンを使う。
- R2 バケットの CORS は `cors.json` をリポジトリに置き、`wrangler r2 bucket cors set` で適用する (Cloudflare の R2 の CORS のドキュメントに記載のコマンド)。
  許可するのはアプリのオリジンからの PUT と、`Content-Type` ヘッダだけとする。
- `pending/` プレフィックスのオブジェクトは R2 のライフサイクルルールで 1 日後に削除する。
  ルールは `lifecycle.json` をリポジトリに置き、`wrangler r2 bucket lifecycle set` で適用する (Cloudflare の R2 のライフサイクルのドキュメントに記載のコマンド)。
- 適用は `mise run r2-setup` タスクで行い、デプロイ手順に含める。`check` には含めない (本番環境に触るため)。
- アカウント削除に伴う一括削除 (`users/<利用者 ID>/` と `pending/<利用者 ID>/` の両方) は 0012 が行う。

## 未確定論点

- PRD は CI が全ての自動テストを実行するとする (制約と前提)。Content-Length と有効期限の検証は R2 の実サービスへのリクエストと資格情報を要するため CI では実行せず、手元で実行して結果を issue 本文に記録する。
  この解釈が所有者の意図と合わない場合は、開発用バケットの資格情報を CI に置いて検証を回す案を PRD の改訂として提案する。

## 完了条件

- Content-Length の検証の結果 (403 の有無と、拒否されない場合の提案の結果) が issue 本文に記録されている。
- 期限切れの URL の拒否の確認方法と結果が issue 本文に記録されている。
- FR-10 の受け入れ基準のうち Backend の分を満たす。
  申告サイズが 5 MB を超える場合の 400、署名の条件 (Content-Type と Content-Length と 5 分の期限)、`pending/` からの移動と `pending/` の削除、紐づけ後の `photo_key` が `pending/` で始まらないこと、確認の失敗時の削除と 400、差し替え時の古いオブジェクトの削除、削除時の `photo_key` の NULL 化、他の利用者の購入の 4 経路が 404 であることを自動テストで確認する。
- 他の利用者の `pending/` のキーを完了通知に渡すと 400 になり、そのオブジェクトが削除されないことを自動テストで確認する。
- 署名の有効期限の値が設定値と一致することを単体テストで確認する。
- 取得の応答に `Cache-Control: private, no-store` が付く。
- 写真の取得が認証済みの利用者だけに成功し、他の利用者の購入では 404 になる。
- 経路の台帳 (0001) に本 issue の 4 経路を追加し、正常系と未認証 401 と入力不正 400 (入力を持つ経路) のテストが揃っている。
- `cors.json` と `lifecycle.json` がリポジトリにあり、`mise run r2-setup` で適用できる。
- R2 のアクセスキーとシークレットの実値が追跡対象のファイルに含まれないことを `git grep` で確認し、実値は `.dev.vars` (git 管理外) と Workers の Secret にだけ置く。
- `mise run check` が通過する。
